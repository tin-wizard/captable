Captable Multitenancy: Architecture Blueprint

Target structure of a multi-company cap-table platform on Next.js, tRPC, Prisma and Neon, linked to the TIN Hub for identity. Version 1 · 2026-10-05 · derived from the code (graph of 534 files, 2,196 nodes, 90 communities) and checked against current library documentation.

BUILT exists in the code today and is covered by tests   TARGET part of the architecture, not yet implemented. This document describes structure; the work sequence is in the separate plan.

1. Architecture at a glance

One application serves many companies. A company is the tenant. A person (User) joins companies through memberships (Member), each with a status and a role. Every request must resolve to exactly one active membership, and every tenant-owned row is reached only through a client scoped to that membership's company. Identity (who the person is) is meant to come from the Hub; authorization inside a company stays in Captable.

2. Tenancy model

Entities

EntityMeaning
CompanyThe tenant. Internal cuid id plus a unique 12-char publicId used in URLs and in storage keys.
UserA person. Global; belongs to no tenant by itself.
MemberUser in Company. Unique on (company, user). Status ACTIVE / INACTIVE / PENDING, isOnboarded, role ADMIN or CUSTOM (+ customRoleId).
CustomRolePer-company list of {subject, actions}. Cannot be shared across companies.

Rules

  • A user may belong to many companies; one membership is active per session.
  • Only an ACTIVE, onboarded member can act. The JWT carries companyId/memberId as hints; they are re-verified against the database on every request.
  • The tenant is flat: no agencies, sub-tenants or workspaces. The Hub has that hierarchy; Captable does not need it.
  • Any signed-in user can create a company and becomes its first ADMIN.

Known limits of the scoped client (design constraints, not defects)

  • It does not cover nested writes (relation connect inside data), relation includes, ids supplied as data (guards cover those), or creates on child models (callers must check the parent).
  • It rewrites any companyId condition to equality, so code that must read another company (listing the user's companies, switching company, accepting an invite) uses the global client on purpose and is allow-listed in the architecture test.
  • Prisma treats an undefined filter value as "do nothing"; that is why identity fields are checked for presence before any lookup.

Tenant switching

The session points at the member with the most recent lastAccessed. switchCompany accepts only the caller's own ACTIVE, onboarded membership, updates lastAccessed and refreshes the session. It deliberately uses the global client because it reads a membership in a different company.

6. Authorization architecture BUILT

A permission is subject:action. ADMIN holds *; CUSTOM holds the list in its CustomRole; a member with no role holds nothing. Enforcement is a tRPC middleware (withAccessControl) driven by .meta({policies}), so a procedure's required permission is visible beside its definition.

Subjects: billing, members, stakeholder, roles, audits, documents, company, developer, bank-accounts, securities, cap-table-settings, updates, data-rooms, templates. The REST API enforces the same check (fail-closed) on stakeholder and share writes, so an API token carries only its owner's role in the company named in the URL.

RuleDefault
Read cap-table dataany active member (exceptions: stakeholders, documents, and anything that mints a public link need their read permission)
Create, edit, delete securities and settingsADMIN or granted
Define or assign roles; invite with a role; act on an ADMINADMIN only (an unchanged role resent by the UI is not a change)

8. Hub integration TARGET

Principle: the Hub owns identity, Captable owns authorization inside a company, and tenant logic is never duplicated. Captable keeps its own Company/Member model and links to the Hub; it does not adopt the Hub's packages, because they depend on Supabase's auth.uid() for isolation and give a Prisma app no protection.
